## Подтверждённая цепочка

1. Карта создаёт заявку по выбранному бункеру; чат получает номер, площадку,
   автора и время. Подтверждено интерфейсом и предоставленным примером чата;
   новая заявка при проверке не отправлялась.
2. Водитель собирает `/b` в черновике и подтверждает сводку. API сохраняет
   вывоз, позиции, вложения и обновление связанных заявок/бункеров.
3. Worker бота доставляет отчёт в кассу Sheets с `submission_key`, маркером
   и повторами. Сценарий ходок `/h` пока пишет в Sheets напрямую.
4. Основной cron `tbank-service` синхронизирует кассу в работы и выставляет
   счета согласно настройкам контрагента.
5. При настроенных интеграциях создаются задача Bitrix24 и письма с файлами;
   отдельные cron обрабатывают банковскую выписку и напоминания.
6. Клиент видит свои бункеры, историю заявок, отчёты, работы и счета.

Фактический пример 16.10.2026 18:45: отчёт №84, бункеры №19 и №22, каждый
с коэффициентом 1,5. Итого: 2 бункера, 3 единицы к оплате, 24 м³ расчётного
объёма, 4 фотографии. Водитель указан по имени.

## Фоновые задачи

Расписание прочитано из root crontab сервера ботов, значения — в timezone
сервера, а не автоматически Europe/Moscow:

| Расписание | Команда |
| --- | --- |
| `*/20 * * * *` | `src.cli.cron` — синхронизация кассы и выставление счетов |
| `*/30 * * * *` | `src.cli.cron_payments` — выписка и сопоставление оплат |
| `0 6 * * *` | `src.cli.cron_invoice_reminders` — напоминания; сама команда учитывает рабочие дни |
| `0 2 * * *` | `src.cli.import_counterparties_to_bitrix24` |

Отдельного `sync_sheets` в crontab нет; он вызывается из `src.cli.cron`,
поэтому это само по себе не ошибка. На хостинге панели запуск Laravel scheduler
через SSH в этой проверке не подтверждён. Прогноз карты виден в интерфейсе.

Для процесса бота:

```bash
service bot-reports status
journalctl -u bot-reports -n 100 --no-pager
journalctl -u bot-reports -f
```

## Рекомендации по результату

1. Проверить HTTPS-редиректы на хостинге панели. Автоматизированный переход
   к URL с завершающим `/admin/` и `/billing/` уходил на `http://.../login`
   в браузере; отдельно подтверждён HTTP 301 downgrade для `/billing/`,
   тогда как URL без завершающего слеша работал по HTTPS. Нужно проверить
   reverse proxy / rewrite и trusted proxy configuration; принудительное
   HTTPS и корректное определение схемы должны исключать downgrade.
2. Контролировать возраст очереди Sheets и последнее успешное выполнение
   cron, а не только наличие процесса. В текущей проверке подтверждены
   отдельные доставленные отчёты, но не вся история фоновой доставки.
3. Для `/h` рассмотреть такой же устойчивый механизм доставки, как для `/b`.
   Сейчас сценарии различаются по поведению при ошибке Sheets.
4. Перед тиражированием отдельно проверить правила доступа к бот-командам,
   ограничения загрузки URL вложений MAX, резервное копирование БД и приватных
   черновиков. В текущем README бота часть этих рисков уже зафиксирована.
5. Перед публичным размещением коммерческих материалов выбрать допустимый
   набор клиентских кейсов и сумм. Подготовленная HTML-презентация автономна,
   письма обезличены, материалы на сайт не публиковались.
